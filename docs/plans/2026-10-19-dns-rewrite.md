## 1. 目标与边界

- 构建部署在 Cloudflare Workers 上的可自定义 DNS 服务。
- 免费套餐是硬约束；本地 workerd 正确性测试不等于线上 CPU 额度验收。
- 不默认继承旧版功能或旧版架构，保留的 README 不能视为新版需求清单。
- 一个部署只有一套 DNS 配置，所有调用者共用；不引入用户账户或多配置隔离。
- 配置保存在仓库文件中，修改后重新部署；不引入在线配置存储或管理页面。
- 采用 TS 配置：声明式规则为主，允许受信任配置中的 JS/TS 条件函数和自定义动作。函数随 Worker 构建，不接受请求提供的代码，不使用运行时 eval。
- 现有 lib/dns-wasm 与 lib/ech-probe 保持独立通用库，业务策略由应用层组合。

## 2. 规则模型

### 结构

一个规则集包含有序规则；每条规则由匹配条件及多个有序动作组成。

    规则集
      规则 1：匹配 → 动作 1 → 动作 2 → …
      规则 2：匹配 → 动作 1 → 动作 2 → …

- 逐条判断规则；匹配后按顺序执行该规则的动作。
- 后续规则读取当前状态，包括此前成功动作产生的修改。
- 保留只读原始查询和上游原始响应，供显式引用。
- 不将条件能力收窄为固定业务场景：支持查询、请求上下文和已有解析结果的组合，并提供函数扩展。
- 只能匹配当前已取得的信息；上游结果条件不能在取得结果前假定其存在。
- 上游查询本身是动作，可与生成自定义答案、修改记录、调整 TTL、ECH 改写、终止等动作组合。
- 自定义记录直接提供答案，响应改写修改已有答案，两者不混为一谈。

### 建议落地默认值，随本规划一并确认

- 每条规则进入时判断一次条件；动作按当前状态依次执行，不在动作之间隐式重跑本条条件。
- 上游查询动作默认以新响应替换当前响应，而不是隐式合并两个答案；需要合并时明确配置或使用扩展动作。
- 默认执行完动作继续下一条规则，不设置隐式循环或跳转。
- 匹配函数异常属于处理错误：记录原因并失败，不当作“不匹配”。
- 原始数据和动作快照不得通过共享可变引用被自定义动作间接破坏。

## 3. 继续、停止和返回

- 继续：处理后续动作和规则。
- 停止规则处理：退出规则集，进入统一响应收尾；没有答案时仍可使用默认上游。
- 直接返回：结束当前动作列表和规则集，进入统一响应收尾；应已有明确响应，没有响应属于执行错误。
- 正常执行到规则集末尾仍没有答案时，查询默认上游；默认上游失败则返回 SERVFAIL。
- 所有返回路径仍经过必要的协议校验、DNSSEC 一致性处理及最终日志，不允许自定义动作绕过收尾。

## 4. 动作失败与可观测性

- 默认动作必需：失败终止本次 DNS 处理，返回 SERVFAIL。
- 显式可选动作：失败时恢复到本动作开始前的 DNS 状态，再继续。
- 不撤销此前成功动作，也不承诺撤销网络请求、日志或其他外部副作用。
- 失败不能静默：包括可选动作失败、回滚、回退、上游失败和 ECH 获取失败。
- 错误事件包含请求标识、规则与动作标识、错误码、错误信息、可用的原因链及最终处置。
- 记录是否回滚、是否继续、是否终止；成功回退不能抹去先前的错误。
- 日志隐藏访问密钥、Authorization、上游凭据等敏感信息；不直接转储整个请求或配置。
- 默认不转储完整 DNS 报文和客户端 IP，诊断详细信息需要显式开启。

## 5. 网络接口与访问控制

- 标准 DoH 必需：RFC 8484 GET/POST、application/dns-message。
- JSON 查询/响应作为可选适配接口，复用同一执行器，不维护第二套规则语义；在阶段三完成。
- 第一版上游采用标准 DoH。
- 访问控制可选：配置密钥后启用，未配置时公开。
- 只接受 Authorization: Bearer <密钥>；不接受路径或查询参数携带密钥。
- 密钥来自 Workers Secret，不提交到配置文件或仓库。
- 普通 DoH 客户端若不支持自定义 Authorization，请求无法使用启用保护的入口；这是已选择的请求头方案的兼容性边界。
- 未通过认证的请求在上游查询、缓存访问及规则执行前拒绝。

## 6. 上游组与响应采用条件

- 上游组具有名称，可以被多条规则引用。
- 支持单上游、顺序回退和并发竞速；不默认并发查询全部服务。
- 上游成功条件可以修改，并提供默认值。
- 默认接受协议有效且对应当前查询的 NOERROR 和 NXDOMAIN，包括合法空答案；默认不将 SERVFAIL/REFUSED 当作成功。
- 网络错误、超时、无效报文等触发该策略配置的失败或回退处理。
- 可以要求目标记录存在，或通过自定义判断决定是否采用响应。
- 竞速返回首个满足条件的 DNS 响应，不以 HTTP 200 或最先完成为唯一标准。
- 未采用的并发请求及时取消并清理资源；全部失败时提供可诊断的聚合原因。
- 查询与动作受总 deadline、请求数量和并发预算约束，避免自由组合产生无界工作。

## 7. 缓存

- 第一版仅缓存上游原始 DNS 响应，不缓存规则执行后的最终答案。
- 缓存命中后仍执行本次请求的条件与动作。
- 缓存身份区分上游、查询及影响解析结果的参数，如 EDNS/ECS、DO/CD；不能只按域名建键。
- 不把请求 ID 等不影响答案的差异作为可跨请求直接复用的响应头；返回时恢复本次请求关联信息。
- 命中时按缓存经过时间递减 TTL；负缓存遵守适用的 DNS 负缓存规则。
- 不自动缓存传输错误、SERVFAIL 等故障结果；无法保证可安全复用的查询绕过缓存。
- 建议使用无需额外数据库绑定的 Workers Cache API；不把缓存视为全局一致或保证命中的持久存储。

## 8. ECH

- ECH 来源由规则明确选择，不设置默认厂商：配置中的 ECHConfigList、指定 DNS HTTPS 记录、主动 TLS 探测结果。
- 来源、缓存及获取时机应显式配置，不因为启用 ECH 改写就默认每条请求进行 TLS 握手。
- 允许规则决定需要哪种来源，不强制所有查询依赖主动探测或后台任务。
- 主动探测默认沿用 lib/ech-probe 的证书验证开启设置；不得为了达到 CPU 目标自动关闭认证。
- 获取失败记录错误，是否使用仍有效的缓存或按可选动作语义保留原响应必须显式表达。
- 不默默使用过期配置、厂商静态兜底或未经认证的替代来源。
- 免费套餐主动探测与刷新的可行性尚待线上 CPU 验证；后台执行或 Cron 不等于免除 CPU 限制。
- 若实测无法满足免费额度，必须报告具体阻塞并重新协商方案，不能静默删功能、改成关闭认证或声称已验收。

## 9. DNSSEC 与输出完整性

- 用户明确允许改写答案，并接受改写可能无法通过下游 DNSSEC 验证。
- 内容被改写时清除 AD，并移除因改写失效的相关签名；不宣称改写后的数据继承原认证状态。
- 未改写的上游内容尽量保留原有 DNSSEC 信息，不无条件剥离全部记录。
- 原始响应缓存不得被改写状态污染。
- 所有输出路径校验消息结构、必要的请求关联信息和响应一致性。

## 10. 分阶段交付

分阶段不缩减最终范围。各阶段独立测试，阶段三完成后才进行完整版本验收。

### 阶段一：规则模型与执行器

交付：TS 配置与校验、声明式条件和函数扩展、多动作执行、当前状态与原始快照、继续/停止/返回、严格失败、可选动作回滚、结构化错误日志。

验收：使用确定性测试动作和 DNS 样例，验证顺序、状态可见性、终止、异常、回滚边界、错误日志及敏感字段脱敏。此阶段不宣称已交付可用网络 DoH 服务。

### 阶段二：可用 DoH 服务

交付：标准 DoH GET/POST、可选 Bearer 认证、单上游/回退/竞速、可修改的默认成功条件、默认上游、原始响应缓存及规则驱动的基本自定义答案和记录修改。

验收：从客户端请求到 DNS 输出的 workerd 端到端测试；缓存 TTL、负答案、失败竞速、超时取消、认证拒绝、DNSSEC 收尾和资源清理均有覆盖。

### 阶段三：增强能力与完整验收

交付：完善内置响应改写动作、按规则选取的 ECH 来源及其缓存/获取策略、可选 JSON 适配接口、部署与规则编写文档。

验收：真实上游和真实 ECH 互操作、DNS WASM/ECH 库回归、冷/热路径及缓存命中/未命中的线上免费套餐 CPU 指标。网络经过时间不作为 CPU 时间；不能只测平均值或仅靠本地测试宣称免费额度适配。

上线测试需要届时单独明确授权，不自动部署到现有业务 Worker。

## 11. 资源与安全底线

- Workers Free 当前每次 HTTP 和 Cron 调用 CPU 额度均为 10 ms；网络等待不计入等待期间的 CPU，报文处理和其他实际计算不能据此忽略。
- 自定义函数是部署者受信任代码，不是沙箱；同步死循环等行为无法靠 Promise 超时安全中止，仍受平台强制限制。
- 对输入大小、动作与查询次数、并发、总耗时、缓存对象等设置明确可配置预算，并提供保守默认值。
- 不从不可信 HTTP 参数直接构建任意 TCP 探测目的地；目的地应来自受信任配置或经过显式校验的规则逻辑。
- 保留现有库的测试与接口，不把业务策略写回通用 DNS/ECH 库。
- 本规划未授权提交、推送或部署；开始实现前需用户确认共同理解。
