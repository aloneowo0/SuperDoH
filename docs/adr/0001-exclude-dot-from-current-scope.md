# Exclude DNS-over-TLS from the current upstream scope

On 2026-10-25 the user approved limiting named DNS upstream transports to HTTPS and ordinary DNS over TCP; every `transport: "tls"` definition, including unused entries, is rejected during whole-configuration preflight, with no automatic transport rewrite or fallback. The reason is that the current native TLS path returned valid DNS answers even with an explicitly incorrect server identity and caching disabled, so it did not reliably enforce the configured independent server-identity requirement; the user chose to narrow scope rather than add another TLS stack ([historical scope discussion in #29](https://github.com/aloneowo0/SuperDoH/issues/29)). This is a product-scope decision, not a claim that Workers cannot support native TLS or that all native TLS paths are infeasible; the independent ECH TLS probe and its verification defaults remain unchanged. If DoT is reconsidered, first revalidate a platform-native TLS path—including identity, deadline/cancellation and protocol behavior—then seek separate acceptance; do not assume this decision passes CPU, ECH, key or other open acceptance criteria.
